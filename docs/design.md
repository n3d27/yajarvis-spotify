# Spotify как плагин YaJarvis — дизайн

Дата: 24-11-26. Статус: согласован 24-11-26.

## Зачем

Spotify можно встроить прямо в ядро YaJarvis, но тогда каждый релиз автора приходится вливать вручную, а поделиться этим с другими нельзя. Автор YaJarvis не принял Spotify в ядро: он предложил плагин в каталоге «От сообщества» (тема GitHub `yajarvis-plugin`).

Цель — плагин, который:
1. даёт Spotify на **обычном** YaJarvis без форка;
2. ставится другим людьми из каталога;
3. сохраняет главное: «включи …» сначала идёт в Spotify, а на время разговора музыка встаёт на паузу. Без паузы ответ Джарвиса не слышен, потому что Soloist (64 бит) и озвучка Джарвиса не могут одновременно занимать звуковое устройство.

## Цели

- Голосом и через модель:
  - включить трек, исполнителя, альбом, плейлист, подкаст;
  - «моё любимое» по порядку, «любимое вперемешку», «рекомендации»;
  - пауза, продолжить, дальше, назад, лайк, дизлайк, перемешать или по порядку.
- Spotify в приоритете: модель зовёт инструмент Spotify первой, а YouTube (`play_music` ядра) — только если Spotify не нашёл или просят видео либо YouTube.
- Пауза Spotify на время разговора с Джарвисом и продолжение после него, только если паузу ставил плагин.
- Если Spotify включили во время разговора, он стартует после ответа, а не поверх голоса.
- Настройки — формой в панели плагина. Статус — в карточке плагина.
- Плагин публикуется в репозитории `n3d27/yajarvis-spotify` с темой `yajarvis-plugin`, релиз — `jarvis-plugin-arm64.zip`.

## Не цели

- Карточка Spotify в плеере панели: плагин не может рисовать свой интерфейс.
- Взаимная остановка YouTube и Spotify.
- Установка самого Spotify-приёмника: Soloist ставится отдельно.
- Поддержка armv7: Soloist в `soloist-station-lite` 64-битный.
- Запрет музыки для Алисы: это не дело плагина.

## Анти-цели

- Плагин тормозит или ломает Джарвиса, если Soloist не запущен, ключей нет или журнал недоступен. Во всех этих случаях плагин тихо уходит в сторону, а статус объясняет, что не так.
- Плагин печатает ключи или токены в журнал, статус или ответы.
- Музыка остаётся на паузе после разговора, хотя её ставил на паузу плагин, а не человек.

## Ограничения

- API плагинов v1 (`jarvis-plugin-sdk`, feature `process`):
  - ядро шлёт плагину только `configure`, `command` (строка, ответ за ≤ 2 с, иначе игнор) и вызовы его инструментов;
  - событий «проснулся» и «разговор окончен» нет;
  - инструменты ядра (`play_music`, `music_control` и др.) перекрывать нельзя.
- Rust-плагин — отдельный процесс с правами `jarvisd`. Рабочая папка — `<data_dir>/plugins/spotify/data`. ФС и сеть доступны.
- На колонке ~16 МБ свободно. Бинарник должен быть порядка 2–4 МБ (статический musl, `opt-level="z"`, strip).
- Сеть плагина идёт напрямую. Spotify должен быть доступен с колонки.
- Журнал ядра: `/tmp/jarvisd/jarvisd.log`. Формат строк — внутреннее дело автора, его могут поменять в любом релизе.

## Подходы (обсуждены, выбран A)

- **A. Rust-плагин, всё локально — выбран.**
  - Управление Soloist идёт через `soloist ctl -w 127.0.0.1:9090`.
  - Поиск и лайки — через Web API Spotify.
  - Пауза на разговор — по журналу ядра.
  - Плюсы: один пакет, мгновенная пауза, не зависит от скриптов `soloist-station-lite`.
  - Минусы: только arm64; паузу сломает смена текста в журнале.
- **B. Lua-плагин и `jarvis-watch.sh` в пакете Soloist.** Отклонён:
  - Песочница Lua не запускает программы и не читает файлы, поэтому управление шло бы через облако (около 1 с и обязательный Premium).
  - Пользователю пришлось бы ставить и связывать две вещи.
- **C. Rust-плагин только через облачный Web API.** Отклонён: пауза доходит через облако за 0,5–1 с, и начало ответа Джарвиса пропадает.

## Как устроен

### Пакет

- `plugin.json`:
  - `id: "spotify"`, `name: "Spotify"`;
  - `kind: "rust"`, `arch: "arm64"`, `api: 1`;
  - `category: "media"`, `icon: "music"`;
  - `provides: ["tools", "commands"]`;
  - `min_core: "0.10.16"`.
- Настройки (`settings`):

  | ключ | тип | смысл |
  |---|---|---|
  | `client_id` | text | Spotify Developer Client ID |
  | `client_secret` | password | Client Secret |
  | `refresh_token` | password | токен пользователя для лайков и «любимого» (как получить — в README плагина) |
  | `liked_uri` | text, необязательно | URI «Любимых треков»; если пусто — вычислить по `GET /v1/me` → `spotify:user:<id>:collection` |
  | `soloist_dir` | text, по умолчанию `/data/opt/soloist` | где стоит Soloist |
  | `pause_on_talk` | toggle, по умолчанию вкл. | пауза на время разговора |

- *Моё решение после проверки:* у Rust-плагина нет способа менять статус в карточке. Для процессных плагинов ядро показывает фиксированное «Rust-пакет», а в SDK нет установщика статуса. Поэтому состояние видно так:
  - по строкам в журнале колонки при старте и при сменах: «spotify-плагин: готов / нет ключей / журнал не найден — пауза на разговор выключена»;
  - по ответу `spotify_control status`: что играет и есть ли проблемы.

  Патчить ядро ради статуса не будем.

### Управление Soloist

- *Моё решение после проверки:* пауза, продолжить, дальше, назад, перемешивание и запуск идут через `sh <soloist_dir>/scripts/control.sh <cmd> [arg]` с `cwd=/`, когда этот скрипт есть. Почему так:
  - `control.sh` и `request_state.sh` берут блокировку и ведут счётчик выбора, поэтому автопереход моста не дерётся с ручным выбором.
  - Перед play и resume они делают `ctl activate` и ждут 0,3 с: за это время озвучка успевает отпустить звуковое устройство. Это важно для продолжения после разговора.
  - «Назад» всегда включает **предыдущий трек** (требование пользователя). Сам Spotify после 3 с трека только перематывает его к началу, поэтому скрипт в таком случае шлёт `prev` дважды. Если плагин работает без `control.sh`, он делает то же самое.

  Порог входа и так «Soloist из `soloist-station-lite`», так что зависимость от его скрипта честная. Если `control.sh` нет, плагин делает то же сам: `ctl activate`, затем 0,3 с, затем `ctl play`/`resume`. Перемотка всегда идёт напрямую через `ctl seek <ms>`, потому что `control.sh` её не принимает.
- Прямой вызов: `LD_LIBRARY_PATH=<soloist_dir>/lib64 <soloist_dir>/bin/soloist ctl -w 127.0.0.1:9090 <команда>` с `cwd=/`.
- Таймауты: 4 с на `now --json`, 8 с на остальное. При таймауте процесс убивается.
- Нужные команды: `now --json`, запуск URI, пауза, продолжить, дальше, назад, перемешивание вкл/выкл, `seek <ms>`. **Точный синтаксис builder берёт из `soloist ctl --help` на колонке.** Известны `seek <ms>` и `now --json`. Как в `ctl` называются play/pause/shuffle, сейчас видно только по `control.sh`/`request_cli` в `soloist-station-lite`.
- Разбор `now --json` опирается на `parse_now` с фикстурами и тестами.

### Поиск и подбор

- Логика поиска и подбора:
  - `SpotifyConf`;
  - `search` (client credentials, кэш токена, повтор один раз при 401);
  - `pick` (нормализация, стоп-слова, порог 0.6, транслитерация кириллицы, предпочтение артиста для `any`);
  - фикстуры поиска.
- «Любимое»:
  - `liked` — перемешивание выкл., затем запуск коллекции. Если после старта `shuffle` всё ещё включён, выключить ещё раз (урок из `search_and_play.sh`).
  - `liked_shuffle` — перемешивание вкл., запуск коллекции. Если `shuffle` сбросился, включить и перейти на следующий трек.
  - `wave` — случайный трек из «Любимых» (`GET /v1/me/tracks`), затем `spotify:station:track:<id>`.
- Ключи (*моё решение*):
  - Порядок чтения: настройки плагина, а если они пусты — `<soloist_dir>/spotify_api.conf`. Так пользователям `soloist-station-lite` идёт без повторного ввода.
  - Если Spotify вернул новый refresh token, он сохраняется в `data/token.json` и используется дальше. Токен из настроек побеждает только тогда, когда его поменяли в панели (сравнивается с запомненным значением).
- Лайк и дизлайк — Web API `PUT`/`DELETE /v1/me/library?uris=<uri текущего трека>` с токеном пользователя (обычный `/v1/me/tracks` на запись отвечает 403 с февраля 2026).

### Инструменты для модели

- `spotify_play {query, kind}`, где `kind`: `any | track | artist | album | playlist | podcast | liked | liked_shuffle | wave`.
  - Описание: «Spotify — основной источник музыки. Любую музыку, песню, исполнителя, альбом, подкаст сначала включай этим инструментом. `play_music` (YouTube) — только если этот ответил „В Spotify не нашёл“ или просят видео, ролик, обзор, „на ютубе“. „Моё любимое“ — kind=liked; liked_shuffle — только если прямо сказали „вперемешку“, „в случайном порядке“, „рандом“.»
  - Ответы:
    - «Включил в Spotify: <Артист> — <Название>.»;
    - «Включил любимое в Spotify.» / «Включил любимое вперемешку в Spotify.» / «Включил рекомендации в Spotify.»;
    - «В Spotify не нашёл „<query>“ — включи через play_music.» (подсказка модели, чтобы она сделала второй вызов);
    - «Spotify не ответил: <коротко>.»
- `spotify_control {command}`, где `command`: `pause | resume | next | prev | like | unlike | shuffle_on | shuffle_off | status`. Описание: «управление тем, что играет в Spotify; если играет Spotify, используй это, а не music_control».
- Известный риск: ядро при выключенной «Яндекс Музыке» говорит модели «любую музыку включай только play_music» (`tools.rs:226`). *Моё решение:* приоритет держат и описание инструмента, и строка в промпте профиля из README («Музыку сначала ищи в Spotify (spotify_play)»). На приёмке это проверяется на настоящей модели (Gemini Live). Если без строки в промпте модель промахивается, README говорит об этом прямо.

### Быстрые команды (`command`, ≤ 2 с)

- Ловятся только точные фразы, без поиска:
  - «лайк», «нравится», «добавь в любимые» → лайк;
  - «дизлайк», «убери из любимых» → дизлайк;
  - «моё любимое» → liked; «любимое вперемешку» → liked_shuffle; «рекомендации», «моя волна» → wave.
- Всё остальное — `null` сразу, чтобы не задерживать ядро.
- Лайк срабатывает, только если Spotify сейчас играет или стоит на паузе с треком. Иначе `null`, и фраза уходит дальше.
- Ответ — короткая фраза («Добавил в любимые.»).
- Запуск «любимого» не укладывается в 2 с, поэтому стартует в фоне, а ответ возвращается сразу.

### Пауза на время разговора (наблюдатель журнала)

- Фоновая задача читает `/tmp/jarvisd/jarvisd.log` с конца, как `tail -F`: переоткрывает файл при усечении или пересоздании, опрашивает раз в 100–200 мс.
- Маркеры (константы в одном месте и тесты на них):
  - **начало** — `Джарвис: активация`;
  - **конец** — `разговор: тишина … окончен`, `разговор прерван`, `разговор не открылся`.
  - **Builder проверяет по исходникам 0.10.18** (`engine.rs`, `cloud_voice.rs`), что это все пути завершения, и что строки не будут перекрыты другими.
- Логика — `TalkPause` (чистая функция с тестами):
  - на начале, если Soloist `playing`, поставить паузу и запомнить URI;
  - на конце продолжить, только если пауза наша, статус `paused`, URI тот же или мы сами переключили трек (`follow`);
  - ручная пауза человека отменяет продолжение;
  - если `spotify_play` вызван во время разговора, запуск откладывается до конца разговора и заменяет продолжение.
- Маркеры сверены с 0.10.18:
  - `engine.rs:601` — «Джарвис: активация»;
  - `engine.rs:1002` — «разговор: тишина … окончен», одна строка на весь разговор, а не на каждую реплику;
  - `engine.rs:1277` — «Джарвис: разговор прерван»;
  - `engine.rs:882` — «разговор не открылся».
- Журнал: сначала `/tmp/jarvisd/jarvisd.log` (на колонке он обычно есть), иначе `<data_dir>/jarvisd.log` (`diagnostics.rs`).
- Страховка: если конца не видно 3 минуты, считать разговор оконченным. Каждое такое срабатывание пишется в журнал («spotify-плагин: не увидел конец разговора»): это признак, что автор поменял строки.
- Повторная активация во время разговора не перезаписывает первую паузу.
- `pause_on_talk = выкл.` отключает наблюдателя.
- Если журнал не найден, статус «пауза на разговор выключена», плагин работает дальше.

### Сборка и выпуск

- Отдельный репозиторий `github.com/n3d27/yajarvis-spotify`, тема `yajarvis-plugin`.
- Зависимость `jarvis-plugin-sdk` (feature `process`) — git-зависимость на `newfpv/YaJarvis`, тег `v0.10.18`. `min_core` — самая ранняя версия ядра с тем же протоколом `api: 1`. Builder сверяет `plugin-sdk` между v0.10.16 и v0.10.18; если протокол не менялся, ставится `0.10.16`. Builder также проверяет, что крейт собирается отдельно от workspace ядра.
- Цель `aarch64-unknown-linux-musl` через `zig cc`.
- `scripts/release.sh` собирает `jarvis-plugin-arm64.zip` (бинарник + `plugin.json`) и проверяет ELF и размер.
- README по-русски:
  - что нужно (Soloist, ключи);
  - как получить refresh token (скрипт или страница авторизации — на выбор builder);
  - строка для промпта профиля;
  - ограничения.

## Приёмка (голосом)

1. «Джарвис, включи Кино» → Spotify.
2. «Джарвис, включи обзор айфона 17» → YouTube (сначала «В Spotify не нашёл…», либо модель сразу берёт `play_music`).
3. «Моё любимое» → по порядку. «Любимое вперемешку» → вперемешку. «Рекомендации» → Spotify.
4. Во время Spotify: «Джарвис, какая погода?» → музыка встаёт, ответ слышен, музыка продолжается.
5. Во время Spotify: «Джарвис, включи Земфиру» → ответ слышен, после него играет Земфира.
6. «Джарвис, лайк» → трек в «Любимых».
7. «Пауза», «дальше» во время Spotify работают.
8. Остановить Soloist (`stop.sh`) → Джарвис отвечает как обычно, плагин в статусе «Soloist не отвечает».
9. Перезагрузка колонки → всё поднимается само.
